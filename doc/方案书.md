## 1. 项目概述

### 1.1 项目背景

面向全国风景线路的旅游电商平台，业务侧需要一套管理后台，用于统一维护线路产品、处理订单、管理客户与客服工单，并通过报表掌握经营情况。一期以管理后台为主体，C 端商城功能仅预留接口与数据结构。

### 1.2 建设目标

- 提供安全可靠的管理员登录与基于角色的权限控制。
- 支持线路产品的全生命周期管理：分类、行程编排、班期价格、上下架、评价查看。
- 支持订单全流程管理：下单记录、支付/退款记录、状态流转、出行人信息。
- 提供经营数据看板与统计报表。
- 支持客服工单与定制游需求跟进。
- 采用 Spring Cloud Alibaba 微服务架构，按业务域拆分为 6 套服务，支持独立部署与扩容。
- 沉淀一套可复用的通用基础模块（common），保证后续扩展的一致性。

### 1.3 一期建设范围

| 范围 | 内容 |
| --- | --- |
| 包含 | 管理员认证、角色权限、线路管理、订单管理、客户管理、运营报表、客服工单、定制需求管理、系统管理（字典/参数/日志/公告/文件）、微信小程序（C 端核心浏览与下单链路） |
| 暂不包含 | App/H5 等其他 C 端形态、真实支付渠道对接（一期模拟支付，二期接微信支付）、真实短信/邮件、高德地图行程可视化（二期接入，见 3.7）、分销与营销活动 |

### 1.4 目标用户与角色

| 角色 | 职责 | 典型权限 |
| --- | --- | --- |
| 超级管理员 | 系统最高权限，维护账号与角色 | 全部菜单与操作 |
| 运营人员 | 维护线路、班期、上下架、标签分类 | 线路管理、部分报表 |
| 订单专员 | 处理订单、退款审核、导出 | 订单管理、客户查看 |
| 客服人员 | 处理工单、跟进定制需求 | 客服、定制、订单只读 |
| 财务/管理者 | 查看经营报表 | 报表、订单只读 |

> 权限模型采用 **RBAC**：管理员 → 角色 → 菜单/按钮权限。同一管理员可拥有多个角色。

### 2.2 服务划分

| 服务 | 职责 | 数据库 |
| --- | --- | --- |
| `RouteGo-gateway` | 统一入口、路由转发、JWT 预校验、限流、跨域、聚合接口文档 | 无（保持无状态） |
| `RouteGo-admin` | 后台登录认证、用户/角色/菜单/权限、字典、参数、操作日志、登录日志、文件、公告 | `routego_admin` |
| `RouteGo-catalog` | 线路分类、线路、行程、图片、标签、班期、评价 | `routego_catalog` |
| `RouteGo-trade` | 订单、出行人、状态流水、支付记录、退款记录 | `routego_trade` |
| `RouteGo-customer` | C 端登录、会员、优惠券模板、用户优惠券 | `routego_customer` |
| `RouteGo-operations` | 客服工单、工单消息、定制需求、定制报价、统计报表 | `routego_operations` |

### 2.3 服务协作方式

| 方式 | 组件 | 使用场景 |
| --- | --- | --- |
| 同步调用 | OpenFeign | 下单校验班期、客服查订单详情、定制成交转订单 |
| 异步消息 | RocketMQ | 支付成功、退款成功、订单超时取消、销量/消费/统计更新 |
| 分布式事务 | Seata AT | 订单创建与班期库存扣减 |
| 注册与配置 | Nacos | 服务注册发现、动态配置、网关路由配置 |
| 服务治理 | Sentinel | 接口限流、熔断、降级 |
| 统一鉴权 | Gateway + JWT | 网关验签，下游做权限码校验 |

### 2.4 架构特点

- **业务库按服务独立**：网关无数据库，5 个有状态服务对应 5 个库，禁止跨库 JOIN，跨服务数据通过 Feign 或 MQ 获取。
- **公共能力下沉**：`common-*` 系列 JAR 统一响应、异常、鉴权、日志、MyBatis、Redis、Feign 客户端。
- **快照解耦**：订单保存线路标题、出发日期、价格快照，不依赖线路服务实时数据。
- **内部接口隔离**：`/internal/**` 仅供服务间调用，网关不对外暴露。
- **独立部署**：6 套服务可单独发布、扩缩容，互不影响。
- **最终一致性**：跨服务写操作通过 MQ + 补偿或 Seata 保证。

### 3.6 选型说明

- **Spring Cloud Alibaba**：Nacos 同时解决注册与配置，Gateway/OpenFeign/Sentinel/Seata 生态完整，国内资料多，适合快速落地。
- **6 套服务**：粒度适中，既体现微服务拆分，又不至于让部署和调用链过重；后续可按流量把订单、支付再拆开。
- **有状态服务独立库**：网关保持无状态，其余服务边界清晰、可独立演进；开发环境可用一个 MySQL 实例建 5 个 schema，生产建议独立实例或独立账号。
- **RocketMQ**：延迟消息解决订单超时取消，事务消息/可靠消息解决支付成功后的销量、消费、统计更新。
- **Seata AT**：订单创建与库存扣减跨服务，用 AT 模式降低侵入；生产也可替换为本地消息表 + 补偿。
- **common 多模块**：公共能力打成 JAR，各服务按需依赖，避免复制粘贴。
- **微信小程序**：C 端入口，原生方案稳定；若后续需要多端，可切换 uni-app（Vue 3 语法）。

### 3.7 地图服务（高德地图）

| 类别 | 技术/能力 | 用途 |
| --- | --- | --- |
| Web 服务 API | 高德开放平台 Web 服务 API（服务端 Key） | 地理编码、逆地理编码、POI 搜索、路线规划、距离矩阵 |
| JS API | 高德 JS API 2.0（管理后台地图选点） | 后台配置线路时在地图上选点 |
| 微信小程序 SDK | 高德微信小程序 SDK 或微信内置地图 | C 端线路地图展示、导航跳转 |
| 坐标系 | GCJ-02（高德/腾讯/微信一致） | GPS 的 WGS-84 需转换，避免坐标偏移 |

生产要求：

- **Key 分离**：服务端 Key 只放后端；前端 JS Key 与小程序 Key 分别配置域名/APPID 白名单。
- **Key 外置**：通过环境变量或配置中心注入，禁止写死在前端或提交仓库。
- **缓存**：地理编码、POI 结果可缓存 30 天，减少调用量与配额消耗。
- **降级**：高德接口超时或失败时，地图模块降级，不影响线路详情、下单主流程。
- **配额告警**：监控调用量与配额，防止 Key 被盗刷。

## 4. 功能模块划分

### 4.1 模块总览

| 编号 | 大模块 | 子功能 |
| --- | --- | --- |
| M1 | 认证与权限 | 登录/登出、验证码、个人信息、修改密码、系统用户管理、角色管理、菜单权限 |
| M2 | 线路管理 | 分类、线路 CRUD、行程编排、图片、标签、班期与价格、上下架、评价查看 |
| M3 | 订单管理 | 订单查询/详情、状态流转、出行人、支付记录、退款审核、导出 |
| M4 | 客户管理 | 会员列表/详情、消费统计、优惠券查看 |
| M5 | 运营报表 | 首页看板、销售趋势、线路销量排行、订单状态分布 |
| M6 | 客服管理 | 工单列表、工单回复、状态处理 |
| M7 | 定制游管理 | 需求单录入/跟进、报价单管理 |
| M8 | 系统管理 | 字典、参数、操作日志、登录日志、公告、文件管理 |
| M9 | 微信小程序（C 端） | 微信登录、线路浏览、下单支付、我的订单、定制需求提交 |

### 4.2 认证与权限（M1）

- 登录：账号 + 密码 + 图形验证码；失败次数限制（可选）。
- 登录成功返回 JWT，前端存入 localStorage，后续请求放在 `Authorization: Bearer <token>`。
- 登出：令牌加入 Redis 黑名单（若启用 Redis）或前端丢弃令牌。
- 系统用户管理：新增、编辑、启用/禁用、重置密码、分配角色。后台账号不只有管理员，还包括运营、订单、客服、财务等工作人员，统一在 `sys_user` 中维护，通过角色区分职责。
- 角色管理：角色 CRUD、分配菜单权限。
- 菜单管理：目录/菜单/按钮三级结构，支持排序与显隐。

### 4.3 线路管理（M2）

- 线路分类：支持一级分类（如自然风光、人文古迹、亲子研学）。
- 线路主信息：标题、副标题、目的地、出发城市、天数、封面、起价、亮点、费用包含/不含、预订须知。
- 行程编排：按天维护行程标题、描述、用餐、住宿、交通、配图。
- 班期管理：出发日期、成人价、儿童价、库存、已售数量、状态。
- 标签与图片：多标签关联、图集排序。
- 上下架与排序：控制 C 端可见性。
- 评价查看：查看用户评分与内容，支持后台回复。

### 4.4 订单管理（M3）

- 订单列表：按订单号、线路、状态、下单时间、联系人筛选。
- 订单详情：线路快照、班期、出行人、金额明细、支付/退款记录、状态流水。
- 状态流转：

```text
待支付 ──支付成功──► 已支付 ──出行──► 出行中 ──结束──► 已完成
   │                    │
   └──取消──► 已取消     └──申请退款──► 退款中 ──审核通过──► 已退款
```

- 退款审核：运营审核退款申请，记录审核人与意见。
- 导出：按筛选条件导出 Excel。
- 一期支付为模拟支付，保留 `payment_record` 表结构，后续可接微信/支付宝。

### 4.5 客户管理（M4）

- 会员列表：手机号、昵称、注册时间、订单数、累计消费、状态。
- 会员详情：基本信息、订单历史、优惠券、消费统计。
- 敏感信息（手机号、身份证）脱敏展示，查看完整信息需更高权限（可选）。

### 4.6 运营报表（M5）

- 首页看板：今日订单数、今日销售额、今日新增客户、待处理工单。
- 销售趋势：按日/周/月统计订单量与销售额（ECharts 折线图）。
- 线路销量 TOP10：按订单数或销售额排序。
- 订单状态分布：饼图。
- 数据来源：`orders`、`customer`、`stat_daily`（可选快照表）。

### 4.7 客服管理（M6）

- 工单列表：工单号、客户、关联订单、类型、优先级、状态、处理人。

## 6. common 通用模块设计

### 6.1 设计目标

- **统一**：所有服务返回格式、异常处理、日志记录、鉴权方式保持一致。
- **解耦**：通用能力与业务代码分离，业务服务只关注自身逻辑。
- **可复用**：6 个服务共享同一套 common JAR，避免复制粘贴。
- **可观测**：异常、慢请求、关键操作、跨服务调用都有 traceId 可追踪。

**微服务下必须拆 Maven 模块**：common 会被所有服务同时依赖，做成独立 JAR 才能统一升级、按需引入、避免版本漂移。当前统一收敛为 `RouteGo-common`，把日志处理、异常处理、统一响应、Feign 客户端、Sentinel 兜底等横切能力都放在这里。

### 6.2 子模块划分

| Maven 模块 | 主要包 | 职责 | 关键类 |
| --- | --- | --- | --- |
| `RouteGo-common` | `com.rg.common` | 统一响应、错误码、异常、日志切面、Feign 客户端、Sentinel 兜底 | `Result`、`ErrorCode`、`BusinessException`、`GlobalExceptionHandler`、`LogAspect`、`*Client` |

依赖关系：

```text
RouteGo-common
   └── 所有业务服务 / 网关按需依赖
```

> 说明：Feign 客户端统一放 `com.rg.common.client`，避免每个服务各写一套；日志、异常、统一响应等横切能力也统一由 common 提供。

#### 6.2.1 统一响应

所有接口返回统一 JSON：

```json
{
  "code": 200,
  "message": "success",
  "data": {},
  "timestamp": 1762128000000
}
```

- `Result.success(data)` / `Result.error(code, message)` 静态工厂方法。
- `ErrorCode` 枚举维护统一错误码：400 参数错误、401 未认证、403 无权限、404 不存在、409 冲突、429 限流、500 系统异常、503 服务不可用。
- 成功码统一为 200；失败时 `Result.code` 与 HTTP 状态码保持一致。

#### 6.2.2 异常处理

- `BusinessException`：业务异常，携带错误码与提示信息，由业务层主动抛出。
- `ErrorCode`：统一错误码枚举，错误码与 HTTP 状态码一致（见 8.4）。
 - `AdminException` / `CatalogException` / `TradeException` / `CustomerException` / `OperationsException`：按微服务拆分，继承 `BusinessException`，统一放在 `com.rg.common.exception.serviceException` 包下。
- `GlobalExceptionHandler`（`@RestControllerAdvice`）统一捕获并转换：

| 异常类型 | 处理方式 |
| --- | --- |
| `BusinessException` 及子类 | 返回业务错误码与提示，HTTP 状态码保持一致 |
| `MethodArgumentNotValidException` / `BindException` | 提取首个字段校验错误，返回 400 |
| `ConstraintViolationException` | 参数校验失败，返回 400 |
| `AccessDeniedException` | 返回 403 |
| `NoHandlerFoundException` | 返回 404 |
| `FeignException` | 返回 503，提示服务暂不可用 |
| `Exception` | 记录 error 日志（含 traceId），返回 500，不暴露堆栈 |

- 生产环境统一返回"系统繁忙，请稍后重试"，详细异常只进日志。

#### 6.2.3 日志处理 `common.log`

分为四类：

1. **操作日志**
   - 注解 `@Log(title = "线路管理", businessType = BusinessType.INSERT)`。
   - `OperLogAspect` 环绕通知，记录：操作人、模块、请求方法、URL、IP、入参、返回结果、耗时、成功/失败、异常信息。
   - 通过异步线程池写入 `sys_oper_log`，避免阻塞主流程；参数与结果做长度截断与敏感字段脱敏。
2. **登录日志**
   - 登录成功/失败均写入 `sys_login_log`，记录账号、IP、浏览器、操作系统、结果、时间。
3. **请求追踪**
   - `TraceIdFilter`（`RouteGo-common`）读取网关传入的 `X-Trace-Id`，没有则生成，放入 MDC；Feign/MQ 调用继续透传。
4. **异常与运行日志**
   - `logback-spring.xml` 配置控制台 + 滚动文件（按天/大小），分级输出；error 日志单独文件。
   - 慢请求（如超过 1s）可单独告警日志（可选）。

#### 6.2.4 认证鉴权 `RouteGo-common`

- 网关 `AuthFilter` 统一校验 JWT 签名与有效期，解析 `userId`、`userType` 写入请求头；登录、验证码、支付回调走白名单。
- 各服务 `JwtInterceptor` 从请求头恢复 `LoginContext`（ThreadLocal），并校验令牌是否在 Redis 黑名单中。
- `PermissionInterceptor` 或方法级 AOP：校验 `@RequiresPermission("route:add")` 所需权限码；权限码由 system 服务写入 Redis，各服务本地缓存。
- 角色/权限变更后，system 发送 MQ 广播事件，各服务清理本地权限缓存，避免长时间不一致。
- 请求结束清理 ThreadLocal，防止内存泄漏。
- 前端配合 `v-permission` 指令控制按钮显隐，后端做最终校验。

#### 6.2.5 参数校验 `RouteGo-common`

- 使用 Jakarta Validation 注解：`@NotBlank`、`@NotNull`、`@Size`、`@Pattern`、`@Min`。
- 自定义注解：手机号 `@Phone`、枚举值 `@EnumValue`、状态 `@Status`。
- DTO 与 Entity 分离，避免直接暴露数据库字段。
- 分组校验：新增（Create）与修改（Update）使用不同校验组。

#### 6.2.6 数据填充 `RouteGo-common`

- `MyMetaObjectHandler` 在 insert 时填充 `createBy`、`createTime`，update 时填充 `updateBy`、`updateTime`。
- 操作人从 `LoginContext` 获取；定时任务/系统操作使用系统账号 ID。

#### 6.2.7 分页与查询 `RouteGo-common`

- `PageQuery`：`pageNum`（默认 1）、`pageSize`（默认 10，上限 100）、排序字段与方向。
- MyBatis-Plus 分页插件统一处理；返回 `PageResult`。
- 查询条件 DTO 继承 `PageQuery`，避免每个接口重复定义分页字段。

#### 6.2.8 缓存 `RouteGo-common`

- `CacheService` 封装 `get/set/delete/expire`，统一序列化方式。
- Key 规范：`travel:{module}:{biz}:{id}`，集中定义在 `RedisKeyConstants`。
- 典型用途：登录令牌、图形验证码、字典缓存、报表短时缓存。

#### 6.2.9 文件存储 `RouteGo-common.storage`

- 定义 `FileStorage` 接口：`upload`、`delete`、`getUrl`。
- 一期实现 `LocalFileStorage`，文件按日期分目录存储，返回可访问 URL。
- 预留 `OssFileStorage` / `MinioFileStorage`，通过配置切换。
- 上传限制：类型白名单（jpg/png/webp/pdf）、大小上限、文件重命名防覆盖。

#### 6.2.10 常量与枚举 `RouteGo-common`

- `CommonConstants`：通用常量（默认页码、令牌前缀、超级管理员 ID 等）。
- `RedisKeyConstants`：缓存 Key 模板。
- 业务枚举：`OrderStatusEnum`、`PayStatusEnum`、`RefundStatusEnum`、`TicketStatusEnum`、`CustomStatusEnum`、`YesNoEnum`，统一提供 `code`、`desc`、`of(code)`。
- 枚举与数据库 tinyint 状态值一一对应，避免魔法数字。

#### 6.2.14 扩展预留（`RouteGo-common` / `RouteGo-common`）

- **防重复提交**：`@Idempotent` 注解 + Redis 键，用于下单、退款等关键操作。

### 6.3 请求处理流程

```text
请求进入
  → Gateway 路由 + JWT 预校验，生成/透传 traceId
  → 目标服务 TraceIdFilter 恢复 traceId
  → JwtInterceptor 校验令牌、写入 LoginContext
  → PermissionInterceptor 校验接口权限
  → Controller 参数校验
  → Service 业务处理（抛 BusinessException 由全局处理器接管）
  → Mapper 数据访问
  → 统一 Result 返回
  → OperLogAspect 异步记录操作日志
  → 清理 ThreadLocal
```

## 7. 数据库设计

### 7.1 设计规范

#### 7.1.1 分库规划

| 数据库 | 归属服务 | 业务表数 | 说明 |
| --- | --- | --- | --- |
| `routego_admin` | `RouteGo-admin` | 15 | 用户、角色、菜单、权限、字典、日志、文件、公告 |
| `routego_catalog` | `RouteGo-catalog` | 8 | 分类、线路、行程、图片、标签、班期、评价 |
| `routego_trade` | `RouteGo-trade` | 5 | 订单、出行人、状态流水、支付、退款 |
| `routego_customer` | `RouteGo-customer` | 3 | 会员、优惠券模板、优惠券 |
| `routego_operations` | `RouteGo-operations` | 5 | 客服工单、工单消息、定制需求、报价、统计 |

> 每个库另含 1 张 Seata AT `undo_log` 基础表，不计入业务表数量。

网关只依赖 Nacos 与 Redis，不创建数据库。开发环境可在一个 MySQL 实例中建 5 个 schema；生产环境建议每个有状态服务使用独立数据库账号，条件允许时独立实例。`sql/schema.sql` 可一次初始化全部 5 个库，`sql/routego_*.sql` 则按服务独立执行。

边界规则：`RouteGo-admin` 只保存后台账号与平台配置；C 端登录和会员身份归 `RouteGo-customer`；商品与班期归 `RouteGo-catalog`；订单、支付和退款归 `RouteGo-trade`；客服、定制游和统计归 `RouteGo-operations`。

#### 7.1.2 建表规范

| 项 | 规范 |
| --- | --- |
| 库名 | 5 个业务库，统一使用 `routego_` 前缀，字符集 `utf8mb4`，排序规则 `utf8mb4_general_ci` |
| 表名 | 小写下划线，按业务域加前缀：`sys_`、`route_`、`order_`、`customer_`、`cs_`、`custom_`、`stat_` |
| 主键 | `id bigint NOT NULL AUTO_INCREMENT` |
| 审计字段 | `create_by`、`create_time`、`update_by`、`update_time`、`deleted` |
| 金额 | `decimal(10,2)`，单位：元 |
| 状态 | `tinyint`，配合数据字典与枚举 |
| 逻辑删除 | `deleted tinyint DEFAULT 0`（0 正常，1 删除） |
| 外键 | **不建物理外键**；同一服务内应用层保证，跨服务只做逻辑引用 |
| 索引 | 唯一业务键建唯一索引；高频查询字段（状态、时间、外键）建普通索引 |
| 字符字段 | 按实际长度设定，避免一律 `varchar(255)` |
| 跨库查询 | **禁止跨库 JOIN**；通过 Feign、MQ 或本地冗余快照解决 |

#### 7.1.3 跨库数据一致性

- **快照冗余**：订单保存线路标题、出发日期、单价、客户昵称等快照，历史订单不依赖源服务。
- **本地事务**：每个服务只保证自己库内事务。
- **跨服务写**：订单 + 库存用 Seata AT；支付成功后用 RocketMQ 通知线路、客户、报表服务。
- **补偿**：消息消费失败进入重试/死信队列，提供人工补偿接口。
- **最终一致**：允许短暂不一致，关键页面展示"处理中"状态。

### 7.2 核心实体关系

```text
[routego_admin]
sys_user ──N:N── sys_role ──N:N── sys_menu
sys_role ──N:N── sys_permission（sys_role_permission）
sys_user ──1:N── sys_user_oauth（第三方登录绑定）

[routego_catalog]
route_category 1──N route
route 1──N route_itinerary / route_image / route_departure / route_review
route N:N route_tag（route_tag_rel）

[routego_trade]
orders 1──N order_traveler / order_status_log / payment_record / refund_record

[routego_customer]
customer 1──N coupon；coupon_template 1──N coupon

[routego_operations]
customer 1──N cs_ticket（逻辑关联，不建外键）
cs_ticket 1──N cs_message
custom_requirement 1──N custom_quote
```

跨库逻辑关系（仅应用层维护，不建外键）：

```text
routego_trade.orders.route_id        → routego_catalog.route.id
routego_trade.orders.departure_id    → routego_catalog.route_departure.id
routego_trade.orders.customer_id     → routego_customer.customer.id
routego_customer.customer.id         → routego_operations.cs_ticket.customer_id
routego_trade.orders.id              → routego_operations.cs_ticket.order_id
```

> 订单表冗余保存线路标题、出发日期、价格、客户昵称等快照字段，避免跨服务实时查询和历史数据漂移。

### 7.6 并发控制与锁设计

#### 7.6.1 四种并发控制手段

| 手段 | 原理 | 适用场景 | 优点 | 代价 |
| --- | --- | --- | --- | --- |
| 分布式锁 | Redis / Redisson 跨实例互斥 | 库存扣减、领券、退款审核、定时任务选主 | 跨节点有效 | 依赖 Redis，需处理锁超时与续期 |
| 数据库悲观锁 | `SELECT ... FOR UPDATE` 行锁 | 冲突高、事务短的更新（退款审核） | 强一致、实现简单 | 阻塞、易死锁、降低并发 |
| 数据库乐观锁 | `version` 版本号 / CAS | 冲突低、读多写少（后台编辑、状态流转） | 无阻塞、性能好 | 冲突时需重试 |
| 原子条件更新 | 单条 `UPDATE` 带条件 | 库存扣减、计数累加 | 最高效、天然防超卖 | 只适合简单条件 |

#### 7.6.2 需要增加 version 字段的表

字段定义：`version int NOT NULL DEFAULT 0`，实体中使用 MyBatis-Plus `@Version` 注解。

| 表名 | 并发场景 | 更新条件示例 |
| --- | --- | --- |
| `sys_user` | 并发编辑、禁用、分配角色 | `UPDATE sys_user SET ..., version = version + 1 WHERE id = ? AND version = ?` |
| `sys_role` | 并发编辑与授权 | 同上 |
| `sys_menu` | 并发编辑菜单 | 同上 |
| `route` | 多人同时编辑线路 | `UPDATE route SET ..., version = version + 1 WHERE id = ? AND version = ?` |
| `route_departure` | 改价、库存调整 | `UPDATE route_departure SET ..., version = version + 1 WHERE id = ? AND version = ? AND stock - sold >= ?` |
| `orders` | 状态流转、退款审核 | `UPDATE orders SET status = ?, version = version + 1 WHERE id = ? AND status = ? AND version = ?` |
| `refund_record` | 退款审核 | `UPDATE refund_record SET status = ?, version = version + 1 WHERE id = ? AND status = ? AND version = ?` |
| `coupon_template` | 发券计数防超发 | `UPDATE coupon_template SET received_count = received_count + 1, version = version + 1 WHERE id = ? AND received_count < total_count AND version = ?` |
| `coupon` | 领取、核销 | `UPDATE coupon SET status = ?, version = version + 1 WHERE id = ? AND status = ? AND version = ?` |
| `cs_ticket` | 并发回复、关闭 | `UPDATE cs_ticket SET status = ?, version = version + 1 WHERE id = ? AND status = ? AND version = ?` |
| `custom_requirement` | 状态跟进 | `UPDATE custom_requirement SET status = ?, version = version + 1 WHERE id = ? AND status = ? AND version = ?` |
| `route_review` | 后台回复 | `UPDATE route_review SET reply = ?, version = version + 1 WHERE id = ? AND version = ?`（可选） |

**不需要 version 字段的表：**

| 类型 | 表 | 原因 |
| --- | --- | --- |
| 追加型流水 | `order_status_log`、`payment_record`、`cs_message`、`custom_quote` | 只插入不更新，用唯一单号约束 |
| 全量覆盖型 | `route_itinerary`、`route_image`、`route_tag_rel` | 同一事务先删后插 |
| 低频配置 | `sys_dict_type`、`sys_dict_data`、`sys_config` | 后台低频操作，数据库行锁足够 |
| 统计快照 | `stat_daily` | 唯一索引 `stat_date` + upsert |
| 日志 | `sys_oper_log`、`sys_login_log` | 只追加，不更新 |

#### 7.6.3 需要悲观锁的场景

| 表 | 场景 | 说明 |
| --- | --- | --- |
| `orders` | 退款审核读取订单并锁定 | `SELECT * FROM orders WHERE id = ? FOR UPDATE`，防止两个管理员同时审核同一订单；也可用分布式锁替代 |
| `route_departure` | 后台强制调整库存 | 低并发场景可短暂 `FOR UPDATE`；热点班期优先用原子条件更新 + 分布式锁 |
| `coupon_template` | 后台批量发券 | 短事务锁定模板行，防止超发 |

**使用要求：**

- 悲观锁必须放在事务内，事务尽量短。
- `SELECT ... FOR UPDATE` 之后禁止远程调用、发消息等耗时操作。
- 加锁顺序统一（如先订单后退款），避免死锁。
- 后台管理类低并发更新优先用乐观锁，不要滥用悲观锁。

#### 7.6.4 各业务推荐组合

| 业务 | 推荐方案 |
| --- | --- |
| 普通后台编辑（用户、角色、菜单、线路） | 乐观锁 `version` |
| 订单状态变更 | 乐观锁 + 状态条件（`WHERE status = ?`） |
| 支付回调 | 唯一索引幂等 + 状态条件更新，不需要锁 |
| 退款审核 | 分布式锁 `lock:refund:{orderId}` + 乐观锁 |
| 库存扣减 | 原子条件更新；热点班期叠加分布式锁，失败提示重试 |
| 优惠券领取 | 分布式锁 + 唯一索引 + 乐观锁 |
| 定时任务 | 分布式锁选主 + 幂等 |
| 统计快照 | 唯一索引 + upsert |

#### 7.6.5 冲突处理约定

- 乐观锁更新影响行数为 0 时，重试最多 3 次；仍失败返回"数据已被修改，请刷新后重试"。
- 分布式锁获取失败返回"操作处理中，请稍后再试"，禁止无限自旋。
- 所有锁操作记录 debug 日志（锁 Key、等待时间、持有时间），便于排查。
- MyBatis-Plus 配置 `OptimisticLockerInnerInterceptor`，逻辑删除与乐观锁可同时使用。

### 7.7 表结构优化清单

> 当前 36 张表可以支撑一期业务，但上线前建议优先处理以下问题。索引必须以
> 真实查询和 `EXPLAIN` 结果为准，不建议一次性给所有状态字段堆索引。

| 优先级 | 问题 | 涉及表 | 建议 |
| --- | --- | --- | --- |
| P0 | 支付与退款回调幂等字段不完整 | `payment_record`、`refund_record` | 为第三方交易号增加唯一索引；退款补充 `channel_refund_id`、失败原因、回调时间；所有回调写入统一 `event_id` |
| P0 | 财务记录仍支持逻辑删除 | `orders`、`refund_record` | 订单和退款记录禁止物理/逻辑删除，关闭使用状态、作废状态或归档表；保留完整审计链 |
| P0 | 订单缺少优惠券快照 | `orders`、`coupon` | 订单增加 `coupon_id`、`coupon_code`、`coupon_amount` 等快照，便于核销、退款和审计，不依赖客户库实时查询 |
| P0 | 软删除与唯一索引冲突 | `sys_user`、`sys_role`、`sys_dict_*`、`route`、`customer`、`coupon` | 明确业务键永不复用；若允许复用，增加 `deleted_token`，将唯一键改为“业务键 + deleted_token”，删除时写入当前 ID |
| P0 | 高频列表查询缺少组合索引 | `orders`、`cs_ticket`、`cs_message`、`route` | 优先评估 `orders(status, create_time)`、`orders(customer_id, create_time)`、`cs_ticket(status, priority, create_time)`、`cs_message(ticket_id, create_time)` |
| P1 | 敏感字段只能加密、难以精确查询 | `order_traveler`、`custom_requirement` | 按业务需要增加手机号/证件号 HMAC 盲索引，并增加 `crypto_key_version` 支持密钥轮换 |
| P1 | JSON 与长文本混用 | `route_review`、`cs_message`、`route`、`sys_oper_log` | 图片数组改用 `JSON` 类型并校验；图片元信息优先拆表；超长请求/响应日志落对象存储，只保留摘要 |
| P1 | 金额精度和事件时间精度不统一 | 全部金额、时间字段 | 金额统一 `decimal(12,2)` 或 `decimal(18,2)`；事件时间建议 `datetime(3)` 并统一存 UTC，展示层再转换时区 |
| P1 | 高增长流水表缺少生命周期策略 | `sys_oper_log`、`sys_login_log`、`order_status_log`、`cs_message` | 按月分区或归档，在线只保留 3–6 个月；日志写入异步化，避免拖慢主业务事务 |
| P1 | 冗余统计值可能与事实表不一致 | `route.sales/rating`、`customer.order_count/total_amount`、`stat_daily` | 消息消费必须用 `event_id` 幂等；增加每日对账与从订单/评价重建统计值的补偿任务 |
| P2 | 关联表保留无业务意义的代理主键 | 用户角色、角色菜单、角色权限、线路标签关联表 | 可改为联合主键，减少一个索引并降低插入开销；分库或分表需要全局 ID 时再保留代理主键 |
| P2 | 字符串排序规则与字段语义不匹配 | 订单号、支付单号、退款单号、权限码 | 业务编号使用 `ascii_bin`，权限码按需使用大小写敏感排序规则；全库升级 MySQL 8 默认 `utf8mb4_0900_ai_ci` |

### 8.4 错误码规范

| 服务 | 异常 |

## 9. 安全设计

| 风险 | 措施 |
| --- | --- |
| 未授权访问 | 网关统一 JWT 验签 + 服务内拦截器；所有后台接口默认需要登录；内部接口禁止公网访问 |
| 越权操作 | 后端基于权限码校验，不能只依赖前端隐藏按钮 |
| 密码泄露 | BCrypt 加盐哈希，禁止明文与可逆加密 |
| SQL 注入 | MyBatis 使用 `#{}` 预编译，禁止字符串拼接 SQL |
| XSS | 富文本白名单过滤；前端渲染转义；设置安全响应头 |
| CSRF | JWT 放在 Header 而非 Cookie，降低 CSRF 风险 |
| 文件上传 | 类型白名单、大小限制、重命名、禁止上传可执行文件 |
| 敏感数据 | 手机号、身份证脱敏展示；证件号加密存储 |
| 暴力破解 | 登录失败次数限制 + 验证码 + 账号锁定（可选） |
| 日志安全 | 日志脱敏，禁止记录密码与完整证件号 |
| 传输安全 | 生产环境启用 HTTPS |
| 令牌失效 | 登出、改密后令牌加入黑名单（Redis） |

## 12. 生产级标准与实施要领

> 本章是项目的生产级建设标准。项目从设计阶段就按生产标准落地，不允许"先做演示版、上线前再补"的方式。业务功能可分期，但安全、日志、幂等、备份等底座能力不能缺。

> 本章涉及的名词（幂等、脱敏、盲索引、乐观锁/悲观锁等）统一解释见 **附录 D**。

### 12.1 总体原则

| 原则 | 生产级要求 |
| --- | --- |
| 安全默认 | 默认拒绝访问、最小权限、敏感数据默认加密与脱敏 |
| 可观测 | 每个请求可追踪、关键指标可监控、异常可告警 |
| 可恢复 | 数据可备份、故障可回滚、操作可审计 |
| 幂等一致 | 关键写操作可重复执行，金额与库存不重复扣减 |
| 配置外置 | 环境相关配置不写死，密钥不入库、不入 Git |
| 分级落地 | P0 上线前必须完成，P1/P2 随业务量演进（见 12.17） |

### 12.2 环境与配置管理

- **三套环境隔离**：dev / test / prod，数据库、Redis、对象存储、密钥全部独立，禁止生产连测试库。
- **配置优先级**：启动参数 > 环境变量 > 配置文件；生产配置不提交仓库。
- **敏感配置外置**：数据库密码、Redis 密码、JWT 密钥、支付密钥、加密主密钥，通过环境变量或配置中心注入；文件中的敏感配置使用 Jasypt 加密。
- **JWT 密钥**：长度 ≥ 256 bit，禁止使用默认值；支持密钥轮换，旧密钥保留一个令牌周期用于验签。
- **接口文档**：生产环境关闭 Knife4j 或增加访问白名单。
- **异常输出**：生产仅返回统一提示，不返回堆栈与 SQL。
- **日志级别**：生产 INFO，异常 ERROR；禁止在日志中输出密码、令牌、完整证件号。

### 12.3 数据安全与加密（分业务）

> 原则：**密码单向哈希；可检索字段"加密 + 盲索引"；展示一律脱敏；传输一律 TLS。**

| 数据/业务 | 加密方式 | 存储形态 | 展示/使用 | 密钥管理 |
| --- | --- | --- | --- | --- |
| 登录密码 | BCrypt（cost 10–12） | 单向哈希密文 | 永不回显 | 盐随哈希存储 |
| 手机号 | AES-256-GCM + HMAC-SHA256 盲索引 | 密文 + 索引列 | 脱敏 `138****8000` | KMS/环境变量，定期轮换 |
| 身份证号 | AES-256-GCM | 密文 | 脱敏 `110***********1234`，明文需授权并审计 | KMS |
| 真实姓名 | 明文 + 展示脱敏（可选加密） | 明文或密文 | 脱敏 `张*` | — |
| 支付回调 | RSA2 / HMAC-SHA256 验签 | 不落密钥明文 | 验签通过才处理 | 支付平台密钥 |
| 接口令牌 | JWT HS256 / RS256 签名 | 客户端持有 | HTTPS 传输 | 私钥与密钥保护 |
| 上传文件 | 私有存储 + 预签名 URL | 私有桶或私有目录 | 鉴权后限时访问（5–15 分钟） | — |
| 数据库/Redis 密码 | Jasypt 加密 / 环境变量 | 不入 Git | 启动时注入 | 配置中心/环境变量 |
| 日志 | 脱敏规则 | 脱敏后明文 | 手机、证件、卡号、密码脱敏 | — |
| 备份文件 | AES-256 加密 | 加密文件 | 恢复时解密 | 离线密钥保管 |

补充规则：

- 加密能力统一封装在 `common.crypto`（如 `AesGcmUtil`、`BlindIndexUtil`），业务代码不直接调用底层算法。
- 加密主密钥不落库；密文带 `keyVersion` 前缀，支持平滑轮换。
- 手机号需要精确查询时，另存 `phone_index`（HMAC 盲索引）列并建索引；模糊查询走脱敏字段或专用检索方案。
- 所有"查看明文"的接口必须校验权限并写审计日志。
- 生产环境全站 HTTPS（TLS 1.2+），开启 HSTS；内部服务间调用也应使用内网加密或 mTLS（P2）。

### 12.4 缓存设计

| 缓存对象 | Key 示例 | TTL | 更新策略 |
| --- | --- | --- | --- |
| 图形验证码 | `captcha:{uuid}` | 2 分钟 | 写入即过期，一次性使用 |
| 令牌黑名单 | `auth:blacklist:{jti}` | 至令牌过期 | 登出/改密时写入 |
| 用户权限与菜单 | `auth:perms:{userId}` | 30 分钟 | 角色或菜单变更时主动删除 |
| 字典数据 | `dict:{dictType}` | 1 小时 | 字典变更时删除 |
| 线路详情 | `route:detail:{id}` | 10 分钟 | 线路更新后删除 |
| 班期余量 | `route:stock:{departureId}` | 5 分钟/实时 | 扣减走 Lua 或分布式锁 |
| 看板数据 | `report:dashboard:{date}` | 5 分钟 | 到期重建或定时刷新 |

缓存问题治理：

| 问题 | 场景 | 治理方案 |
| --- | --- | --- |
| 缓存穿透 | 查询不存在的线路/字典 | 空值缓存 60 秒；可选布隆过滤器 |
| 缓存击穿 | 热点 key 过期瞬间大量请求打到库 | 互斥锁重建 + 逻辑过期 |
| 缓存雪崩 | 大量 key 同一时间过期 | TTL 加随机抖动；多级缓存 |
| 一致性 | 线路、字典更新后读到旧值 | 先更新数据库，事务提交后删除缓存；失败重试；必要时延迟双删 |
| 大 key | 线路图集、长列表缓存 | 拆分存储、限制集合大小 |
| 热 key | 首页线路、热门班期 | 本地缓存 + Redis 两级；热点探测 |

实现要求：

- 统一使用 JSON 序列化，禁用 JDK 原生序列化。
- Key 统一 `travel:{module}:{biz}:{id}` 规范，集中定义在 `RedisKeyConstants`。
- 所有缓存必须设置 TTL，禁止永久 key（配置白名单除外）。
- 缓存不能作为唯一数据源，必须可随时从数据库重建。

### 12.5 分布式锁

| 场景 | 锁 Key | 实现方式 | 说明 |
| --- | --- | --- | --- |
| 库存扣减 | `lock:stock:{departureId}` | Redisson RLock 或 Lua | 锁内校验余量并扣减 |
| 订单创建防重 | `lock:order:create:{userId}:{departureId}` | `SET NX PX` | 配合客户端幂等 token |
| 退款审核 | `lock:refund:{orderId}` | Redisson RLock | 防止并发重复退款 |
| 优惠券领取 | `lock:coupon:{templateId}:{customerId}` | `SET NX PX` | 防止超领 |
| 定时任务选主 | `lock:job:{jobName}` | Redisson RLock | 多实例只允许一台执行 |
| 缓存重建 | `lock:cache:rebuild:{key}` | `SET NX PX` | 防止击穿 |
| 报表生成 | `lock:report:{date}` | Redisson RLock | 防止重复计算 |

实现要求：

- 统一使用 Redisson `RLock`，或 `SET key value NX PX` + Lua 脚本释放（释放前校验持有者）。
- 锁粒度按资源划分：库存按班期、退款按订单、领券按模板 + 客户。
- 必须设置等待时间与持有超时；业务耗时不确定时启用看门狗续期。
- 锁内完成"校验 + 扣减 + 写流水"；事务在锁内提交后再释放锁（`TransactionSynchronization.afterCommit` 或把锁放在事务外层）。
- 获取锁失败返回明确业务提示（如"当前人数较多，请稍后重试"），禁止无限自旋。
- 定时任务必须用锁选主，即使当前单实例部署也要预留。

### 12.6 幂等设计

| 场景 | 幂等键 | 方案 |
| --- | --- | --- |
| 支付回调 | 支付单号 | 唯一索引 + 状态机判断 |
| 下单 | 客户端 requestId | Redis `SETNX` 10 分钟，或防重表 |
| 退款申请/审核 | 退款单号 | 唯一索引 + 订单状态校验 |
| 批量导入 | 文件 MD5 + 操作人 | Redis 记录，重复文件直接拒绝 |
| 消息消费（P2） | messageId | 消费记录表或 Redis 去重 |

通用要求：

- 幂等能力封装为 `IdempotentService`，支持 Redis 与防重表两种实现。
- 数据库唯一索引是最终兜底，即使 Redis 失效也不能重复入账。
- 重复请求返回首次处理结果，不返回错误，避免调用方误判。

### 12.7 限流、熔断与降级

| 接口/场景 | 建议阈值 | 策略 |
| --- | --- | --- |
| 登录 | 5 次/分钟/IP | 滑动窗口 |
| 图形验证码 | 1 次/60 秒/手机号或 IP | 固定窗口 |
| 下单 | 10 次/分钟/用户 | 令牌桶 |
| 导出 | 3 次/分钟/用户 | 滑动窗口 |
| 全局 API | 按压测容量设定 | 网关或 Sentinel 集群限流 |

要求：

- 单机限流使用 Sentinel 或 Bucket4j，集群限流使用 Redis + Lua。
- 被限流返回 HTTP 429 与统一错误码，前端提示"操作过于频繁，请稍后再试"。
- 第三方支付、短信调用设置连接/读取超时、重试上限与熔断；失败进入降级逻辑并告警。
- 核心链路（登录、下单、支付）优先保障，非核心链路（报表、导出）可降级或排队。

### 12.8 消息队列与异步（RocketMQ）

- 适用场景：订单超时取消（延迟消息）、支付成功/退款成功事件、销量与消费更新、报表汇总、操作日志异步落库。
- 可靠性要求：消息持久化、生产确认、消费手动 ACK、失败重试 + 死信队列、消费幂等（业务单号唯一键）。
- 消息体统一放 `common-mq`，包含 `messageId`、`bizNo`、`eventType`、`timestamp`、`traceId`。
- 生产建议：RocketMQ 集群部署；消费失败进入死信队列并告警，提供人工补偿接口。
- 降级：MQ 不可用时，核心链路先落本地库并记录待发送事件，恢复后补发；非核心异步任务可暂停。

### 12.9 分布式事务与一致性

| 场景 | 涉及服务 | 方案 |
| --- | --- | --- |
| 创建订单 + 扣减班期库存 | trade → catalog | Seata AT：订单本地事务 + 库存服务分支事务，失败全局回滚 |
| 支付成功后的销量/消费/统计更新 | trade → catalog / customer / operations | RocketMQ 事务消息或可靠消息 + 消费幂等，最终一致 |
| 退款成功后的库存/金额回滚 | trade → catalog / customer | MQ 事件 + 补偿任务 |
| 定制成交转订单 | operations → trade | Feign 同步创建，失败重试；或 MQ 异步 |
| 客服工单关联订单/客户 | operations → trade / customer | Feign 只读查询，不参与事务 |

实施规则：

- 每个服务只保证自己数据库的本地事务，禁止跨库事务。
- Seata AT 的 `undo_log` 已内置在五个业务库（基础表，不计入 36 张业务表），结构与 Seata 官方 MySQL 版本一致。
- `@GlobalTransactional` 只加在入口方法（如下单），事务内不做过长耗时操作。
- 跨服务远程调用必须有超时、重试上限与降级；重试接口必须幂等。
- 支付回调、退款回调以业务单号 + 状态做唯一约束，重复回调直接返回成功。
- MQ 消费失败重试 3 次后进入死信队列，记录补偿任务并告警。
- 每日对账：订单金额、支付流水、退款流水、优惠券核销、库存销量。
- 长流程（定制、退款审核）优先用状态机 + 补偿，不强行套分布式事务。

### 12.10 数据库生产要求

- 连接池使用 HikariCP，最大连接数按 `CPU 核数 × 2 + 磁盘数` 评估，生产建议 20–30。
- 慢 SQL 阈值 1 秒，开启慢查询日志，每周审查并优化。
- 所有查询走索引；禁止 `SELECT *`；禁止在索引列上使用函数或隐式转换。
- 每日全量备份 + binlog 增量备份；备份文件加密；每月至少一次恢复演练。
- 单表超过 500 万行或 10 GB 时启动归档或分表方案。
- 应用数据库账号最小权限，禁止 DROP/ALTER；DDL 走变更流程。
- 网关不建库；5 个有状态服务各用自己的 `routego_*` 数据库。服务只连接自己的库；读写分离、单库分表列为 P2 预留，表结构无物理外键、含业务主键，便于后续扩展。

### 12.11 可观测性

- **统一 traceId**：网关生成，Feign 请求头、RocketMQ 消息头透传，日志、SQL、MQ 消费都带同一 traceId。
- **结构化日志**：JSON 格式，包含服务名、实例、traceId、userId、耗时、结果码。
- **链路追踪**：Micrometer Tracing + Zipkin（P1）；SkyWalking（P2，支持拓扑与慢调用分析）。
- **指标监控**：各服务 `/actuator/prometheus`，Prometheus 采集，Grafana 展示。
- **关键指标**：QPS、P95/P99、错误率、JVM/GC、连接池、缓存命中率、Feign 超时率、MQ 堆积、Seata 事务失败数。
- **服务治理监控**：Sentinel Dashboard 查看限流/熔断；Nacos 查看实例健康状态。
- **告警**：错误率 > 1%、P95 > 1s、MQ 堆积 > 1 万、支付回调失败、Seata 全局事务失败、实例下线。
- **日志保留**：在线 15–30 天，冷备 6 个月；敏感字段脱敏后再落盘。

### 12.12 安全防护（OWASP）

| 风险 | 生产级措施 |
| --- | --- |
| 越权访问 | 接口级权限码校验 + 数据归属校验（水平越权） |
| SQL 注入 | MyBatis `#{}` 预编译，禁止拼接 SQL |
| XSS | 富文本白名单过滤、输出转义、CSP 响应头 |
| CSRF | 令牌放 Header，不使用 Cookie 承载会话 |
| 文件上传 | 扩展名 + MIME + 文件头校验，重命名存储，禁止目录穿越 |
| 反序列化 | 禁止接收不可信序列化数据，Jackson 关闭危险特性 |
| SSRF | 服务端请求外部 URL 时做域名白名单 |
| 依赖漏洞 | 定期执行 Dependency-Check / npm audit |
| 信息泄露 | 关闭调试端点、隐藏版本号、统一错误响应 |
| 暴力破解 | 登录锁定 + 验证码 + 失败审计 |

### 12.13 部署与发布

- 6 套服务分别打包为可执行 jar / Docker 镜像，独立发布、独立扩缩容。
- 每个服务固定 JVM 参数，开启 GC 日志；容器设置 CPU/内存限制与健康检查。
- 配置集中在 Nacos，按 `namespace + group + dataId` 隔离环境；敏感配置用 Jasypt/KMS 加密。
- 数据库变更按服务管理：每个服务维护自己的 `db/migration`，用 Flyway/Liquibase 执行，禁止跨库 DDL。
- 发布顺序：`admin` → `catalog` / `customer` → `trade` → `operations` → `gateway`；网关最后发布以切换流量。
- 采用滚动发布或蓝绿发布；新实例健康检查通过后再摘除旧实例。
- 开启优雅停机（`server.shutdown=graceful`），等待在途请求与 MQ 消费完成。
- 每次发布保留上一版本镜像与配置，支持 5 分钟内回滚。
- 网关统一 TLS、HSTS、gzip、请求体大小与超时；内部服务不暴露公网端口。

## 附录 C：业务逻辑清单

> 按模块列出关键业务规则、校验条件、状态流转与边界处理，作为开发与测试的依据。

### C.1 认证与权限

| 编号 | 业务逻辑 |
| --- | --- |
| A01 | 登录校验：账号存在 → 未禁用 → 密码 BCrypt 匹配 → 验证码正确（可选） |
| A02 | 登录失败 5 次锁定 10 分钟（次数与时长可配置）；成功登录后失败计数清零 |
| A03 | 登录成功生成 JWT（userId、username、过期时间 2 小时），记录最后登录时间/IP，写登录日志 |
| A04 | 登录失败也要写登录日志，记录账号、IP、失败原因 |
| A05 | 登出时令牌加入 Redis 黑名单，保留至原过期时间 |
| A06 | 修改密码：校验旧密码 → 校验新密码强度 → 更新 → 该用户全部令牌失效 |
| A07 | 新增用户：用户名唯一、初始密码符合强度、至少分配一个角色 |
| A08 | 不能停用或删除当前登录账号；超级管理员账号受保护 |
| A09 | 禁用用户后其令牌立即失效，无法继续访问 |
| A10 | 角色编码唯一；内置角色不可删除；角色下有用户时禁止删除 |
| A11 | 分配菜单时校验菜单存在；菜单有子级或已被角色引用时禁止删除 |
| A12 | 超级管理员角色默认拥有全部权限，权限判断直接放行 |
| A13 | 权限双层控制：后端校验权限码（最终防线），前端 `v-permission` 控制按钮显隐 |
| A14 | 所有后台接口默认需要登录，登录、验证码等白名单接口显式放行 |

### C.2 线路管理

| 编号 | 业务逻辑 |
| --- | --- |
| B01 | 分类最多 2 级；同级下名称唯一；存在子分类或已关联线路时禁止删除 |
| B02 | 线路编号唯一；标题、目的地、出发城市、天数必填；天数 ≥ 1 |
| B03 | 线路必须归属一个存在且启用的分类 |
| B04 | 新建线路默认下架状态，需人工上架 |
| B05 | 上架校验：有封面图、有行程安排、至少一个可售班期（可按实际放宽） |
| B06 | 下架不影响已产生订单，仅影响 C 端展示与下单 |
| B07 | 有订单引用的线路禁止物理删除，只能下架或逻辑删除 |
| B08 | 行程按天维护，`day_no` 从 1 开始连续，建议与线路天数一致；保存采用全量覆盖（先删后插） |
| B09 | 图片、标签、行程保存在同一事务内，任一失败整体回滚 |
| B10 | 标签名称唯一；删除标签需先解除与线路的关联 |
| B11 | 同一线路同一出发日期只能有一个班期（唯一索引兜底） |
| B12 | 班期库存 ≥ 0，已售 ≤ 库存；成人价 > 0，儿童价可为空 |
| B13 | 有订单的班期不可删除，只能停售；停售不影响已售订单 |
| B14 | 班期改价只影响新订单，历史订单使用下单时快照价 |
| B15 | 线路起价取所有可售班期的最低价，班期变动时同步更新 |
| B16 | 评分 1–5；线路平均评分由有效评价聚合计算 |
| B17 | 后台可回复评价，记录回复内容与时间；已删除评价不参与评分计算 |

### C.3 订单管理

#### 状态流转矩阵

| 当前状态 | 操作 | 目标状态 | 前置条件 |
| --- | --- | --- | --- |
| 待支付（0） | 支付成功 | 已支付（1） | 金额与订单一致、班期可售 |
| 待支付（0） | 主动取消 | 已取消（4） | 有操作权限、填写取消原因 |
| 待支付（0） | 超时自动取消 | 已取消（4） | 创建超过 30 分钟未支付 |
| 已支付（1） | 开始出行 | 出行中（2） | 到达出发日期（可手工触发） |
| 出行中（2） | 行程结束 | 已完成（3） | — |
| 已支付（1） | 申请退款 | 退款中（5） | 未出行、金额合法 |
| 出行中（2） | 申请退款 | 退款中（5） | 按业务规则允许时 |
| 退款中（5） | 审核通过 | 已退款（6） | 退款审核权限 |
| 退款中（5） | 审核驳回 | 回退原状态 | 必须填写驳回原因 |
| 已取消 / 已完成 / 已退款 | — | 终态 | 不允许再次流转 |

#### 业务规则

| 编号 | 业务逻辑 |
| --- | --- |
| C01 | 下单校验：线路上架、班期可售、余量充足（库存 − 已售 ≥ 人数）、日期未过 |
| C02 | 库存采用条件更新防超卖：`UPDATE ... SET sold = sold + n WHERE stock - sold >= n` |
| C03 | 一期采用**下单预占库存**，超时取消或主动取消时释放已占库存 |
| C04 | 金额计算：单价 × 人数 − 优惠金额；实付金额不得小于 0 |
| C05 | 订单号全局唯一，格式见 C.11；生成冲突时重试 |
| C06 | 订单保存线路标题、出发日期、单价快照，线路后续修改不影响历史订单 |
| C07 | 支付回调必须幂等：同一支付单号重复回调只处理一次（唯一索引 + 状态判断） |
| C08 | 支付成功：订单状态置为已支付、写支付记录、累加线路销量、写状态流水、记录支付时间 |
| C09 | 支付金额与订单实付金额不一致时拒绝回调并记录异常日志 |
| C10 | 只有待支付订单可取消；已支付订单取消必须走退款流程 |
| C11 | 取消订单：释放库存、写状态流水、记录取消时间与原因 |
| C12 | 退款金额 ≤ 实付金额；退款单号唯一；一个订单可有多次退款（部分退款预留） |
| C13 | 退款审核通过：更新订单为已退款、写退款记录、回滚销量、按规则回滚库存 |
| C14 | 退款驳回：订单回到申请前状态，记录审核人、时间、驳回原因 |
| C15 | 出行人姓名必填，证件号按线路要求校验；证件号加密存储、展示脱敏 |
| C16 | 出行人数需与班期余量匹配，儿童与成人按对应价格计算 |
| C17 | 订单导出受权限控制，单次导出上限 1 万条，导出行为记操作日志 |
| C18 | 订单查询、详情、导出均需权限校验；客服角色只读 |
| C19 | 订单与库存、流水、支付记录的写操作在同一事务内完成 |

### C.4 客户管理

| 编号 | 业务逻辑 |

## 附录 D：核心概念与并发控制速查

### D.1 幂等（Idempotency）

**定义**：同一个请求执行一次和执行多次，对系统产生的最终结果相同。

**幂等不是字段**，它是一种设计原则。实现时通常需要一个"幂等键"（idempotency key），这个键可以是：

- 业务字段：支付单号 `pay_no`、退款单号 `refund_no`、订单号 `order_no`
- 客户端参数：下单时前端生成的 `requestId`
- 消息字段：`messageId`

**例子**：支付平台因为网络抖动把同一个支付结果回调了 3 次。如果每次回调都执行 `sold = sold + 1`，库存会被扣 3 次；正确的做法是识别出这是同一笔支付，只处理第一次。

**实现手段**：

| 手段 | 说明 |
| --- | --- |
| 唯一索引 | `pay_no`、`refund_no` 唯一，重复插入直接失败 |
| 状态机判断 | 只有"待支付"订单才能改成"已支付"，已支付再次回调直接返回成功 |
| Redis SETNX | 下单时用 `requestId` 占位，重复请求直接拒绝 |
| 防重表 | 记录已处理的业务键，处理前查询 |

### D.2 脱敏（Masking / Desensitization）

**定义**：展示时隐藏部分字符，例如手机号 `138****8000`、身份证 `110***********1234`。

**脱敏不是字段**，是展示规则，通常通过 Jackson 序列化器或注解在返回前处理。

**容易混淆的四个概念：**

| 手段 | 是否可逆 | 用途 | 示例 |
| --- | --- | --- | --- |
| 加密 | 可逆 | 存储敏感数据，需要还原 | AES-256-GCM 加密手机号 |
| 哈希 | 不可逆 | 密码校验 | BCrypt |
| 脱敏 | 不改变数据 | 展示层遮盖 | `138****8000` |
| 盲索引 | 不可逆 | 加密后仍能精确查询 | `HMAC-SHA256(手机号)` |

> 一句话：**加密管存储，脱敏管展示，哈希管密码，盲索引管查询。**

### D.3 盲索引（Blind Index）

手机号用 AES 加密后，数据库里是一串密文，无法直接 `WHERE phone = ?` 查询。做法是额外存一列 `phone_index = HMAC-SHA256(phone, 密钥)`，查询时对输入做同样计算再匹配。

- 索引列不可逆，泄露也无法还原手机号。
- 密钥必须与数据分开保管。
- 适用于手机号、身份证等需要精确查询的加密字段。

### D.4 缓存穿透、击穿、雪崩

| 名词 | 含义 | 例子 | 解决 |
| --- | --- | --- | --- |
| 缓存穿透 | 查询一个**根本不存在**的数据，缓存和数据库都没有 | 恶意请求不存在的线路 ID | 空值缓存、布隆过滤器、参数校验 |
| 缓存击穿 | **一个热点 key 过期**瞬间，大量请求打到数据库 | 首页爆款线路缓存到期 | 互斥锁重建、逻辑过期 |
| 缓存雪崩 | **大量 key 同时过期**或 Redis 宕机 | 凌晨统一过期 | TTL 加随机值、多级缓存、Redis 高可用 |

### D.5 分布式锁

**定义**：多个服务实例同时操作同一资源时，用 Redis 等外部组件实现跨进程互斥。

- 典型实现：Redisson `RLock`，或 `SET key value NX PX` + Lua 脚本释放。
- 必须设置过期时间，防止宕机后死锁；业务耗时长时用看门狗续期。
- 释放时要校验锁的持有者，不能直接 `DEL`。
- 锁的粒度要细：按班期 ID、订单 ID 加锁，不要一把全局锁。

### D.6 乐观锁与悲观锁

| 对比项 | 乐观锁 | 悲观锁 |
| --- | --- | --- |
| 核心思想 | 假设冲突很少，更新时检查版本号 | 假设冲突很多，先锁住再操作 |
| 实现 | `version` 字段 / CAS | `SELECT ... FOR UPDATE` |
| 是否阻塞 | 不阻塞 | 阻塞其他事务 |
| 适用 | 读多写少、后台编辑、状态流转 | 冲突高、事务短的强一致场景 |
| 失败处理 | 影响行数为 0，重试或提示刷新 | 等待锁释放，注意死锁 |
| 本项目的表 | `sys_user`、`sys_role`、`sys_menu`、`route`、`route_departure`、`orders`、`refund_record`、`coupon_template`、`coupon`、`cs_ticket`、`custom_requirement` | `orders`（退款审核）、`route_departure`（后台调库存）、`coupon_template`（批量发券） |

> 详细的表级锁方案见 **7.6 并发控制与锁设计**。

### D.7 原子条件更新

一条 SQL 同时完成"判断 + 修改"，依赖数据库行锁保证原子性，不需要额外加锁：

```sql
UPDATE route_departure
SET sold = sold + #{count}, version = version + 1
WHERE id = #{id}
  AND stock - sold >= #{count}
  AND version = #{version};
```

影响行数为 0 说明余量不足或版本冲突，业务层据此提示或重试。库存扣减优先用这种方式，比悲观锁性能好。

### D.8 限流、熔断、降级

| 名词 | 含义 | 例子 |
| --- | --- | --- |
| 限流 | 限制单位时间内的请求量 | 登录 5 次/分钟/IP |
| 熔断 | 下游持续失败时暂时切断调用，避免拖垮自己 | 支付接口连续超时后直接返回失败 |
| 降级 | 核心功能不可用时返回兜底结果 | 报表服务挂了，看板显示缓存数据 |

### D.9 最终一致性

强一致性要求所有节点同时成功，成本和延迟高。最终一致性允许中间短暂不一致，但通过重试、补偿、对账保证最终一致。

- 本项目订单与支付流水在 `routego_trade` 内，属于本地强一致；订单与班期库存在两个服务库，用 **Seata AT** 保证全局一致。
- 支付成功后的销量、客户消费、统计更新用 **RocketMQ + 消费幂等 + 对账补偿**实现最终一致。
- 长流程（退款审核、定制成交）优先用状态机 + 补偿，不强行套全局事务。

### D.10 其他常用术语

| 术语 | 解释 |
| --- | --- |
| 灰度发布 | 先让少量用户使用新版本，观察无问题再全量 |
| 优雅停机 | 停止接收新请求，等待在途请求处理完再退出 |
| 幂等键 | 用于识别重复请求的唯一标识 |
| 乐观锁版本号 | 表中 `version` 字段，每次更新 +1 |
| 防重表 | 记录已处理业务键的表，用于幂等 |
| 逻辑删除 | 用 `deleted = 1` 标记删除，不物理删除数据 |
| 数据脱敏 | 展示时遮盖敏感信息 |
| 盲索引 | 加密字段的可查询索引 |

### E.1 系统与权限域（15 张）

#### 1. `sys_user` 系统用户表

- **对应模块**：RouteGo-admin / 系统管理。
- **建议接口**：`/admin/system/user`（当前脚手架为 `/admin/sysUser`，建议统一到文档规范）。
- **业务操作**：
  - 分页列表：按账号、昵称、手机号、状态、角色、创建时间筛选；不返回密码。
  - 详情：基本信息 + 已分配角色；手机号按权限脱敏。
  - 新增：用户名唯一、初始密码符合强度、至少分配一个角色；手机号加密并写盲索引（A07）。
  - 编辑：昵称、头像、邮箱、手机号、备注；用户名不允许修改；使用 `version` 乐观锁。
  - 启用/禁用：不能停用自己；超级管理员受保护；禁用后立即踢下线（A08、A09）。
  - 重置密码：管理员操作，不校验旧密码；校验新密码强度；重置后踢下线。

  - 分配角色：事务内替换 `sys_user_role`；至少一个角色；校验角色存在且启用。
  - 修改自己的密码：校验旧密码、校验强度，改完重新登录（A06）。
- **关联与事务**：`sys_user_role` 同事务；角色变化后清权限缓存并踢下线。
- **横切能力**：权限码 `system:user:*`；写操作审计；手机号加密、盲索引、脱敏；登录失败锁定在登录流程（A02）。

- **对应模块**：RouteGo-admin / 系统管理。
- **建议接口**：`/admin/system/role`。
- **业务操作**：
  - 分页列表、详情（含菜单与权限点）、新增、编辑、启用/禁用、删除。
  - 分配菜单：维护 `sys_role_menu`；分配权限：维护 `sys_role_permission`。
  - 查看角色下用户：分页只读。
- **关键规则**：`role_code` 唯一；内置角色不可删除；角色下有用户时禁止删除（A10）；超级管理员默认拥有全部权限（A12）。
- **关联与事务**：`sys_user_role`、`sys_role_menu`、`sys_role_permission` 同事务替换；变更后清权限缓存。
- **横切能力**：权限码 `system:role:*`；审计；`version` 乐观锁。

#### 3. `sys_user_role` 用户角色关联表

- **业务定位**：用户与角色的多对多关系，不单独作为业务资源暴露。
- **业务操作**：随“用户分配角色”批量替换；按用户查角色、按角色查用户。
- **关键规则**：`(user_id, role_id)` 唯一；用户、角色必须存在且角色启用。
- **关联与事务**：与 `sys_user` 编辑同事务；变更后清该用户权限缓存。
- **横切能力**：不单独记审计，由用户/角色操作统一记录。

#### 4. `sys_menu` 菜单表

- **对应模块**：RouteGo-admin / 系统管理。
- **建议接口**：`/admin/system/menu`。
- **业务操作**：
  - 树形列表、详情、新增、编辑、删除、排序、显示/隐藏、启用/禁用。
  - 按当前用户角色返回可见菜单树（动态路由）。
- **关键规则**：`menu_type` 为 M 目录 / C 菜单 / F 按钮；父级必须存在且不能形成环；有子级或已被角色引用时禁止删除（A11）；`perms` 与权限码对应。
- **关联与事务**：`sys_role_menu` 引用；菜单变化后清权限缓存。
- **横切能力**：权限码 `system:menu:*`；审计；`version` 乐观锁。

#### 5. `sys_role_menu` 角色菜单关联表

- **业务定位**：角色可见菜单关系，不单独暴露。
- **业务操作**：随“角色分配菜单”批量替换；按角色查菜单。
- **关键规则**：`(role_id, menu_id)` 唯一；菜单必须存在；分配结果影响前端动态路由。
- **关联与事务**：与角色编辑同事务；变更后清权限缓存。

#### 6. `sys_permission` 权限点表

- **对应模块**：RouteGo-admin / 系统管理。
- **建议接口**：`/admin/system/permission`。
- **业务操作**：分页列表、详情、新增、编辑、启用/禁用、删除；按模块分组查询。
- **关键规则**：`permission_code` 唯一，命名遵循 `模块:动作`；已被角色引用时禁止删除。
- **关联与事务**：`sys_role_permission` 引用；权限点变化后清权限缓存。
- **横切能力**：权限码 `system:permission:*`；审计。

#### 7. `sys_role_permission` 角色权限关联表

- **业务定位**：角色与权限点的关系，不单独暴露。
- **业务操作**：随“角色分配权限”批量替换；按角色查权限码。
- **关键规则**：`(role_id, permission_id)` 唯一；权限点必须存在且启用。
- **关联与事务**：与角色编辑同事务；变更后清权限缓存，必要时 MQ 广播各模块清本地缓存。

#### 8. `sys_user_oauth` 后台用户第三方登录绑定表

- **对应模块**：RouteGo-admin / 系统管理。
- **建议接口**：`/admin/system/user-oauth`。
- **业务操作**：绑定列表、绑定第三方账号、解绑；按用户查绑定。
- **关键规则**：`(provider, openid)` 唯一；同一用户同一平台只保留一个绑定；解绑前必须确认用户仍有密码或其他登录方式。
- **安全要求**：只存 openid/unionid/昵称/头像，不存第三方 token、secret；绑定/解绑需审计。
- **关联与事务**：与 `sys_user` 关联；不参与登录主流程的事务。

#### 9. `sys_dict_type` 字典类型表

- **对应模块**：RouteGo-admin / 系统管理。
- **建议接口**：`/admin/system/dict/type`。
- **业务操作**：分页列表、详情、新增、编辑、启用/禁用、删除。
- **关键规则**：`dict_type` 唯一；删除前必须先删除其下字典数据（H02）。
- **关联与事务**：`sys_dict_data` 引用；变更后删除字典缓存（H03）。
- **横切能力**：权限码 `system:dict:*`；审计。

#### 10. `sys_dict_data` 字典数据表

- **对应模块**：RouteGo-admin / 系统管理。
- **建议接口**：`/admin/system/dict/data`。
- **业务操作**：按类型分页/列表、新增、编辑、删除、排序、启用/禁用、设默认项。
- **关键规则**：同一 `dict_type` 下 `dict_value` 唯一；类型必须存在且启用；同一类型默认项只保留一个（应用层保证）；被业务引用的字典值不随意删除。
- **关联与事务**：字典变更后刷新缓存（H03）；订单状态等强业务状态仍以代码枚举为准，字典只负责展示文案。
- **横切能力**：权限码 `system:dict:*`；审计。

#### 11. `sys_config` 系统参数表

- **对应模块**：RouteGo-admin / 系统管理。
- **建议接口**：`/admin/system/config`。
- **业务操作**：分页列表、按 key 查询、新增、编辑、删除；支持批量更新。
- **关键规则**：`config_key` 唯一；敏感参数（密钥、第三方凭证）加密存储，接口不明文回显（H04）。
- **关联与事务**：参数变更后刷新配置缓存；影响业务阈值（如登录锁定次数）时提示生效范围。
- **横切能力**：权限码 `system:config:*`；审计。

#### 12. `sys_oper_log` 操作日志表

- **对应模块**：RouteGo-admin / 系统管理。
- **建议接口**：`/admin/system/oper-log`（只读）。
- **业务操作**：分页查询、详情、导出；按模块、操作人、状态、IP、时间范围筛选。
- **关键规则**：只追加不修改，不提供新增/编辑/删除接口（H08）；在线保留不少于 6 个月（H09）；导出行为本身也要记审计。
- **写入方式**：由操作日志切面异步写入，参数与结果脱敏、截断；超长内容只留摘要。
- **横切能力**：权限码 `system:operlog:list/export`；查询导出记日志。

#### 13. `sys_login_log` 登录日志表

- **对应模块**：RouteGo-admin / 系统管理。
- **建议接口**：`/admin/system/login-log`（只读）。
- **业务操作**：分页查询、导出；按账号、IP、状态、时间筛选。
- **关键规则**：登录成功和失败都写入（A03、A04）；只追加；保留建议 3 个月（H09）。
- **写入方式**：登录流程异步记录，不阻塞登录响应。
- **横切能力**：权限码 `system:loginlog:list/export`。

#### 14. `sys_file` 文件记录表

- **对应模块**：RouteGo-admin / 文件管理。
- **建议接口**：`/admin/system/file`。
- **业务操作**：上传、分页列表、详情、获取访问地址、删除。
- **关键规则**：类型白名单（jpg/png/webp/pdf）、大小上限、重命名防覆盖（H06）；删除记录时同步删除物理文件或标记待清理（H07）；私有文件鉴权访问，不能裸露 URL（I10）。
- **存储方式**：`storage_type` 支持本地、OSS、MinIO；对外返回预签名或限时 URL。
- **横切能力**：上传限流；权限码 `system:file:*`；审计；图片可异步做内容安全检查。

#### 15. `sys_notice` 公告表

- **对应模块**：RouteGo-admin / 系统管理。
- **建议接口**：`/admin/system/notice`。
- **业务操作**：分页列表、详情、新增、编辑、删除、发布/下架、置顶。
- **关键规则**：标题必填；发布时写 `publish_time`；过期公告不展示（H05）；置顶优先排序。
- **关联与事务**：无强关联；C 端/后台首页查询已发布且未过期的公告。
- **横切能力**：权限码 `system:notice:*`；审计。

### E.2 线路域（8 张）

#### 16. `route_category` 线路分类表

- **对应模块**：RouteGo-catalog / 线路管理。
- **建议接口**：`/admin/route/category`。
- **业务操作**：树形列表、详情、新增、编辑、删除、排序、启用/禁用。
- **关键规则**：最多 2 级；同级下名称唯一；存在子分类或已关联线路时禁止删除（B01）；父级不能是自己或子孙。
- **关联与事务**：`route.category_id` 引用；删除前校验线路引用。
- **横切能力**：分类树缓存；权限码 `route:category:*`；审计。

#### 17. `route` 线路主表

- **对应模块**：RouteGo-catalog / 线路管理。
- **建议接口**：`/admin/route`。
- **业务操作**：
  - 分页列表、详情、新增、编辑、删除、上架/下架、排序。
  - 详情聚合：分类、行程、图片、标签、班期、评价摘要。
  - 保存线路时同时保存行程、图片、标签（B09）。
- **关键规则**：`route_no` 唯一；标题、目的地、出发城市、天数必填且天数 ≥ 1（B02）；分类必须存在且启用（B03）；新建默认下架（B04）；上架校验封面、行程、可售班期（B05）；下架不影响已产生订单（B06）；有订单引用禁止删除（B07）。
- **起价与统计**：`min_price` 取可售班期最低价（B15）；`sales` 由支付成功事件累加；`rating` 由有效评价聚合。
- **关联与事务**：主表 + 行程 + 图片 + 标签同事务；班期独立维护；删除前校验订单引用。
- **横切能力**：线路详情缓存 10 分钟，更新后删除；`version` 乐观锁；权限码 `route:*`；审计；索引覆盖 `status`、`category_id`、`create_time`。

#### 18. `route_itinerary` 行程明细表

- **对应模块**：RouteGo-catalog / 线路管理。
- **建议接口**：随线路保存，如 `/admin/route/{id}/itinerary`；不单独提供完整 CRUD。
- **业务操作**：按天查询、随线路新增/编辑/删除。
- **关键规则**：`day_no` 从 1 开始连续，建议与线路天数一致（B08）；保存采用全量覆盖（先删后插）；坐标使用 GCJ-02。
- **关联与事务**：与 `route` 保存同事务；任一失败整体回滚（B09）。
- **横切能力**：缓存随线路详情；不单独审计。

#### 19. `route_image` 线路图片表

- **对应模块**：RouteGo-catalog / 线路管理。
- **建议接口**：随线路保存，如 `/admin/route/{id}/images`。
- **业务操作**：图集查询、上传、排序、删除。
- **关键规则**：图片 URL 必须来自文件服务；保存采用全量覆盖；限制单线路图片数量与单图大小。
- **关联与事务**：与 `route` 保存同事务；缓存随线路详情。
- **横切能力**：不单独审计，由线路保存统一记录。

#### 20. `route_tag` 标签表

- **对应模块**：RouteGo-catalog / 线路管理。
- **建议接口**：`/admin/route/tag`。
- **业务操作**：分页列表、新增、编辑、删除、排序、启用/禁用。
- **关键规则**：`tag_name` 唯一；删除前先解除与线路的关联（B10）；停用标签不再用于新线路。
- **关联与事务**：`route_tag_rel` 引用。
- **横切能力**：标签列表缓存；权限码 `route:tag:*`；审计。

#### 21. `route_tag_rel` 线路标签关联表

- **业务定位**：线路与标签的多对多关系，不单独暴露。
- **业务操作**：随线路保存批量替换；按线路查标签、按标签查线路。
- **关键规则**：`(route_id, tag_id)` 唯一；标签必须存在且启用。
- **关联与事务**：与 `route` 保存同事务。
- **横切能力**：不单独审计。

#### 22. `route_departure` 出发班期表

- **对应模块**：RouteGo-catalog / 班期管理。
- **建议接口**：`/admin/route/{routeId}/departure`。
- **业务操作**：
  - 分页列表、详情、新增、编辑、删除、停售/恢复。
  - 改价、库存调整；按日期/状态筛选可售班期。
- **关键规则**：同一线路同一出发日期只能有一个班期（B11）；库存 ≥ 0、已售 ≤ 库存、成人价 > 0、儿童价可空（B12）；有订单的班期不可删除，只能停售（B13）；改价只影响新订单，历史订单用快照价（B14）。
- **库存扣减**：优先原子条件更新 `stock - sold >= n`；热点班期叠加分布式锁（C02、C03）；取消/退款按规则释放或回滚库存。
- **关联与事务**：下单与库存、订单、流水同事务；定时任务同步线路起价（B15）。
- **横切能力**：余量缓存 5 分钟，扣减后更新缓存；`version` 乐观锁；权限码 `route:departure:*`；审计。

#### 23. `route_review` 线路评价表

- **对应模块**：RouteGo-catalog / 评价管理。
- **建议接口**：`/admin/route/review`。
- **业务操作**：分页列表、详情、隐藏/显示、后台回复、删除（逻辑）。
- **关键规则**：评分 1–5；一个订单只能评价一次（B16）；已删除/隐藏评价不参与评分计算（B17）；回复记录内容与时间；后台回复需权限。
- **关联与事务**：`order_id` 唯一；回复更新评价并聚合线路评分；C 端评价需校验订单属于当前客户且已完成。
- **横切能力**：评价内容过 UGC 内容安全检查；线路评分/详情缓存更新；权限码 `route:review:*`；审计；`version` 乐观锁。

### E.3 订单域（5 张）

#### 24. `orders` 订单主表

- **对应模块**：RouteGo-trade / 订单管理。
- **建议接口**：`/admin/order`。
- **业务操作**：
  - 后台代录、分页列表、详情、取消、状态流转、导出。
  - 状态操作：支付成功、开始出行、完成、申请退款、审核通过/驳回、超时取消。
- **关键规则**：
  - 下单校验线路上架、班期可售、余量充足、日期未过（C01）；库存条件更新防超卖（C02）；下单预占库存，取消释放（C03）。
  - 金额 = 单价 × 人数 − 优惠，实付不小于 0（C04）；订单号唯一（C05）。
  - 保存线路标题、出发日期、单价快照，后续线路修改不影响历史订单（C06）。
  - 只有待支付可取消；已支付取消必须走退款（C10、C11）；终态不可再流转。
  - 导出受权限控制，单次上限 1 万条，导出行为记日志（C17）；客服角色只读（C18）。
  - 订单不提供删除接口，财务记录不做逻辑删除。
- **关联与事务**：订单 + 出行人 + 状态流水 + 库存扣减同事务（C19）；支付、退款、销量、客户消费、统计通过事件或同库事务完成。
- **横切能力**：下单幂等（`requestId`）、支付回调幂等（`pay_no` + 状态机）、退款幂等（`refund_no`）；创建锁 + 库存锁/条件更新；超时取消用延迟消息 + 定时兜底；联系人手机号加密/脱敏；审计；`version` 乐观锁。

#### 25. `order_traveler` 出行人表

- **对应模块**：RouteGo-trade / 订单管理。
- **建议接口**：随订单保存，如 `/admin/order/{id}/travelers`。
- **业务操作**：随订单新增/编辑/删除；订单详情返回出行人列表。
- **关键规则**：姓名必填；证件号按线路要求校验；成人/儿童类型影响价格；证件号、手机号加密存储、展示脱敏（C15）；人数与班期余量匹配（C16）。
- **修改边界（建议）**：待支付可修改；已支付后变更需走客服/人工流程并留痕。
- **关联与事务**：与订单创建同事务；全量覆盖保存。
- **横切能力**：加密、脱敏；不单独审计，由订单操作记录。

#### 26. `order_status_log` 订单状态流水表

- **业务定位**：订单状态变更的追加型流水，不单独暴露。
- **业务操作**：随每次状态变更写入；按订单查询时间线。
- **关键规则**：记录 `from_status`、`to_status`、操作人、备注、时间；只追加，不修改、不删除。
- **关联与事务**：与订单状态变更同事务（C19）。
- **横切能力**：随订单详情展示；权限随订单查询。

#### 27. `payment_record` 支付记录表

- **对应模块**：RouteGo-trade / 支付管理。
- **建议接口**：`/admin/payment`（查询）。
- **业务操作**：支付回调写入、按订单/支付单号查询、财务对账；一期支持模拟支付。
- **关键规则**：
  - `pay_no` 唯一；第三方交易号建议唯一（P0 优化项）；支付金额必须与订单实付一致，不一致拒绝并记录异常（C09）。
  - 支付回调幂等：唯一索引 + 订单状态判断，重复回调返回成功（C07）。
  - 支付成功更新订单、写流水、记状态日志、累加销量（C08）。
  - 只追加，不修改、不删除；冲正通过新记录或退款流程处理。
- **关联与事务**：与订单支付状态更新同事务；支付成功后发事件给线路、客户、统计。
- **横切能力**：回调验签、幂等、审计、对账任务；不缓存。

#### 28. `refund_record` 退款记录表

- **对应模块**：RouteGo-trade / 退款管理。
- **建议接口**：`/admin/refund`。
- **业务操作**：申请退款、分页列表、详情、审核通过、审核驳回、退款回调。
- **关键规则**：
  - `refund_no` 唯一；退款金额 ≤ 实付金额（C12）；一个订单可多次退款，预留部分退款。
  - 状态：0 待审核、1 已通过、2 已驳回、3 已退款。
  - 审核通过：订单置为已退款、写退款记录、回滚销量、按规则回滚库存（C13）；驳回回退原状态并记录原因（C14）。
  - 审核必须记录审核人、时间、意见；退款回调幂等；不提供删除接口，财务记录不可逻辑删除。
- **关联与事务**：退款单 + 订单状态 + 库存/销量回滚同事务；退款回调异步通知客户与统计。
- **横切能力**：退款审核分布式锁 + `version` 乐观锁；退款回调幂等；财务权限；审计。

### E.4 客户与营销域（3 张）

#### 29. `customer` 会员表

- **对应模块**：RouteGo-customer / 会员管理。
- **建议接口**：`/admin/customer`（后台）；`/app/customer`（C 端）。
- **业务操作**：
  - C 端：微信登录、绑定手机号、个人中心、修改资料。
  - 后台：分页列表、详情、启用/禁用、匿名化处理；按手机号/会员等级筛选。
- **关键规则**：手机号唯一，通过盲索引精确查询（D01）；禁用后不能登录 C 端，但历史订单可查（D02）；订单数、累计消费由支付/退款事件增减且不小于 0（D03）；会员等级按累计消费自动升级（D04）；有订单禁止物理删除，只能禁用或匿名化（D06）。
- **关联与事务**：与订单、优惠券关联；支付成功/退款成功更新累计值。
- **横切能力**：手机号、身份证、姓名加密/脱敏；查看明文需权限并审计（D05）；登录限流；会员详情可短缓存；审计。

#### 30. `coupon_template` 优惠券模板表

- **对应模块**：RouteGo-customer / 优惠券管理。
- **建议接口**：`/admin/coupon/template`。
- **业务操作**：分页列表、详情、新增、编辑、删除、启用/禁用、批量发券。
- **关键规则**：名称、类型（满减/折扣）、门槛、金额/折扣率、总量必填；`total_count >= received_count`；固定区间或领取后 N 天二选一；停用不影响已领取的券；已发放的模板不删除。
- **关联与事务**：批量发券生成 `coupon`；发放计数用条件更新 + 锁防超发（D07）。
- **横切能力**：模板缓存；领取锁；权限码 `coupon:template:*`；审计；`version` 乐观锁。

#### 31. `coupon` 用户优惠券表

- **对应模块**：RouteGo-customer / 优惠券管理。
- **建议接口**：`/admin/coupon`（查询）；`/app/coupon`（领取、我的券）。
- **业务操作**：领取、分页列表、详情、使用核销、退款返还、过期处理。
- **关键规则**：
  - `code` 唯一；状态：0 未使用、1 已使用、2 已过期。
  - 使用校验：未使用、未过期、满足门槛、归属当前客户（D08）。
  - 整单退款返还、部分退款不返还（D09）；过期由定时任务置为已过期（D10）。
  - 领取受模板总量与每人限领数量限制（D07）。
- **关联与事务**：下单时核销，订单取消/退款按规则返还；核销与订单同事务；幂等键可用订单号 + 券码。
- **横切能力**：领取分布式锁 + 唯一索引 + `version`；模板余量缓存；审计。

### E.5 客服域（2 张）

#### 32. `cs_ticket` 客服工单表

- **对应模块**：RouteGo-operations / 客服管理。
- **建议接口**：`/admin/cs/ticket`。
- **业务操作**：创建（后台代建/C 端）、分页列表、详情、分配处理人、状态流转、重开、删除（仅管理员）。
- **关键规则**：
  - `ticket_no` 唯一；标题、类型、内容必填（F01）。
  - 关联订单时必须存在且属于该客户，后台代建可放宽（F02）。
  - 状态：待处理 → 处理中 → 已解决 → 已关闭；已关闭可重开（F03）。
  - 首次回复自动进入处理中并记录处理人（F04）；已关闭默认不可回复（F06）。
  - 高优先级在列表置顶/标红（前端展示规则，F07）；删除仅管理员且记审计（F08）。
- **关联与事务**：首次回复更新工单与写入 `cs_message` 同事务；详情聚合客户/订单只读摘要。
- **横切能力**：`version` 乐观锁；权限码 `cs:ticket:*`；审计；不缓存。

#### 33. `cs_message` 工单消息表

- **业务定位**：工单往来消息，追加型，不单独暴露完整 CRUD。
- **建议接口**：`/admin/cs/ticket/{id}/message`。
- **业务操作**：发送消息、按工单分页查询、查看历史消息。
- **关键规则**：区分客户/系统用户发送方；内容或图片至少一项；已关闭工单不可发送；首次管理员回复更新工单状态与处理人；只追加，不修改、不删除。
- **关联与事务**：与工单状态变更同事务；消息内容做 UGC 安全检查。
- **横切能力**：后台回复审计；内容含敏感信息时展示脱敏；不缓存。

### E.6 定制游域（2 张）

#### 34. `custom_requirement` 定制需求表

- **对应模块**：RouteGo-operations / 定制游管理。
- **建议接口**：`/admin/custom/requirement`。
- **业务操作**：创建（后台代录/C 端）、分页列表、详情、分配跟进人、状态跟进、关闭、成交转订单（可选）。
- **关键规则**：
  - `requirement_no` 唯一；联系人、电话、目的地必填并校验手机号格式（G01）。
  - 支持未注册客户代录（G02）；状态：待跟进 → 已报价 → 已成交 / 已关闭（G03）。
  - 关闭必须填写原因；已成交不可直接关闭（G04）；报价后需求自动置为已报价（G06）。
  - 跟进人变更记录审计（G09）；成交转订单一期可作为可选能力（G08）。
- **关联与事务**：`custom_quote` 引用；报价与需求状态更新同事务；成交转订单与订单创建同事务或可靠事件。
- **横切能力**：联系电话加密/脱敏；权限码 `custom:requirement:*`；审计；`version` 乐观锁；不缓存。

#### 35. `custom_quote` 定制报价表

- **对应模块**：RouteGo-operations / 定制游管理。
- **建议接口**：`/admin/custom/requirement/{id}/quote`。
- **业务操作**：新增报价、按需求查询报价列表、详情、采纳、标记失效。
- **关键规则**：
  - 一个需求可多次报价，每次独立记录金额、明细、有效期（G05）。
  - `quote_no` 唯一；金额 > 0（G06）；有效期过后不可采纳，需重新报价（G07）。
  - 状态：0 待确认、1 已采纳、2 已失效；采纳后需求置为已成交，其他待确认报价置为失效（同事务）。
  - 追加型记录，不提供删除接口。
- **关联与事务**：与需求状态更新同事务；采纳后可触发转订单流程。
- **横切能力**：权限码 `custom:quote:*`；审计；不缓存。

### E.7 统计域（1 张）

#### 36. `stat_daily` 每日经营统计表

- **对应模块**：RouteGo-operations / 运营报表。
- **建议接口**：`/admin/report`（查询与重算）。
- **业务操作**：
  - 每日 01:00 生成前一日快照（E10）；按日期查询；支持按日期重算。
  - 看板聚合：今日订单数、销售额、新增客户、待处理工单、订单状态分布、线路排行、销售趋势。
- **关键规则**：
  - `stat_date` 唯一；指标包括订单数、已支付订单数、销售额、退款金额、新增客户数。
  - 销售额按支付时间统计实付金额并排除已退款（E02）；趋势无数据日期补 0（E05）；排行排除已取消/已退款订单（E06）。
  - 报表数据范围按角色控制（E08）；看板缓存 5 分钟（E09）。
- **数据来源与一致性**：订单、支付、退款、客户事件通过 MQ 或定时聚合写入；每日对账与从事实表重建（§7.7 P1）；重算操作记审计。
- **横切能力**：看板缓存 5 分钟；权限码 `report:*`；审计重算操作；不提供手工新增/编辑/删除快照的接口。

### E.9 实施建议

1. **先系统域**：`sys_user`、`sys_role`、`sys_menu`、`sys_permission` 及其关联表，把登录、权限、菜单跑通。
2. **再线路域**：`route_category` → `route`（含行程、图片、标签）→ `route_departure` → `route_review`。
3. **然后订单域**：`orders` → `order_traveler` → `order_status_log` → `payment_record` → `refund_record`，库存与状态机是重点。
4. **客户与营销**：`customer` → `coupon_template` → `coupon`，注意领取/核销并发。
5. **最后运营域**：`cs_ticket`/`cs_message`、`custom_requirement`/`custom_quote`、`stat_daily`。
6. 每张主表实现时同步补齐：权限码、审计注解、参数校验、唯一索引兜底、状态机校验、事务边界。
